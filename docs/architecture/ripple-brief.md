Status: public VersionCompass interface, confirmed by the owner October 29, 2026. The October 28 release delivered direct main-site navigation and bespoke teal/slate workspace chrome. Public home: https://versioncompass.com/ripple. Transparency: https://versioncompass.com/ripple/updates.

## Purpose and audience

Help Cisco practitioners trace an upstream CVE to a supported product relationship, bounded per-CVE evidence, remaining uncertainty and an actionable next check. Include Splunk and acquired Cisco portfolios. Public availability is delivered; comprehensive portfolio coverage is still being built. A package match, KEV entry, severity or integration relationship alone does not establish Cisco impact.

## Product and operating boundaries

The public VersionCompass workspace is read-only. The existing Ripple Site remains owner-private and owns D1 research, collection, assessment and bounded research writers. Do not make the private backend public to implement public-facing product status. Keep credentials server-side and use supported hidden-stdin service access. Customer versions and watchlists stay in the browser and outside exports/shared links. No inventory uploads, scans, tracking, analytics or new connected-app dependency.

Retain the existing daily schedule and the 150-request UTC-day collection cap, including retries. Substantive evidence research requires an admitted 12-minute session, at most five sessions and 60 reserved minutes daily. Respect next-review dates, persist evidence/gaps/next actions and independently read back outcomes. Only reviewed unchanged fingerprints support calibrated claims. Keep original verification dates for unchanged claims and retain prior evidence during outages.

Public status does not remove evidence gates. The existing noindex/nofollow policy is an indexing choice, not access control; changing it is outside this update.

## Continuous improvement

Treat Ripple as a first-class interface alongside VersionCompass's other public destinations. Preserve its bespoke chrome and shared navigation. Use observed visitor journeys, evidence gaps, source failures and operating measurements to propose small, useful UI/UX and data-quality improvements. Record each proposal's user problem, scope, expected value, effort, evidence/verification gate and target review date. Prefer improving the value of existing evidence before increasing collection breadth.

Routine refresh/assessment writes data without redeployment. Bounded interface, calibration or parser improvements use the appropriate existing source/publication workflow, exact-candidate tests, affected browser/export checks, repository/Sites parity and live verification. Larger scope, privacy changes, paid services and new timers require separate owner direction. Do not redesign the chrome during intelligence maintenance. Never treat a target date as delivery evidence.
